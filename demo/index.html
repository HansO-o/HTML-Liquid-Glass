在普通网页上做液态玻璃

这是一张普通的 HTML 页面，文字、图片、表格、表单都是真实 DOM。顶部导航条、图片上的卡片、右边的圆形按钮和参数面板都是 SDK 做的玻璃。拖动按钮，或者在参数面板里新建几块面板试试。

浏览器不让 JS 读页面像素

页面里可能有跨域图片、iframe、访问过的链接颜色，如果 JS 能直接读到渲染结果，这些信息就会泄露。所以没有任何浏览器提供“读取某块区域像素”的接口，WebGL、WebGPU、three.js 也绕不过去。SDK 按浏览器自动选引擎：

原生滤镜

Chrome · Edge · 安卓 · Electron

元素加上 backdrop-filter: url(#滤镜)，位移图按光学模型生成。浏览器在 GPU 上直接折射实时页面，没有截图，也没有延迟。

快照 + WebGL

Safari · iOS · Firefox

把 DOM 克隆一份，连同页面样式表放进 SVG，让浏览器重新画成低分辨率纹理。WebGL 只画边缘那圈折射，中间用 CSS 模糊直接显示实时页面。

CSS 兜底

没有 WebGL 2 的环境

只有 CSS 毛玻璃、压暗和高光，没有折射。

为什么边缘用快照就够了

液态玻璃只有边缘一圈会折射。边缘宽度设成 6% 时，按钮 94% 以上的面积都是平的，光线直接穿过，只叠一层模糊、压暗和提亮。快照引擎让这部分始终显示实时页面，只有最外面那圈细边来自快照。

那圈细边里的内容被压缩、翻转过，分辨率降到一半甚至四分之一也看不出来；快照偶尔慢半拍，也只影响这几个像素宽的地方。下面这些色块适合拿来测试：

实时图层

canvas 和 video 不需要重拍整页。给它们加上 data-lg-live，玻璃经过时 SDK 每帧把它们的画面直接写进纹理，所以边缘里的波形也是实时在动的。

拍不到的内容：挖空

iframe、video、读不到的跨域图片、无限循环的 CSS 动画，快照要么拍不到，要么只能拍到冻住的一帧。快照引擎会在纹理里把这些区域挖成透明：玻璃经过时，中间直接显示实时内容，只做模糊和压暗；边缘不再折射，改成一圈玻璃拟态的高光，不会出现错位或冻住的画面。

这个均衡器是无限循环的 CSS 动画。SDK 能自动发现正在播放的无限动画；这里给容器加了 data-lg-hole，让整块一起挖空。第三方组件、地图这类内容也可以手动这样标记。

靠近就融合

同一层（同一个父元素下、相同 z-index 和定位方式）、同一种材质的玻璃不会互相压出边缘。两块玻璃的距离小于 blend（默认 24px）时，形状开始像水滴一样连在一起；叠在一起时重叠的部分没有内边缘，高光和投影也只沿着整体的外轮廓走。

融合以后，原生引擎在这组玻璃最下面那块里面放一块共用的背板：按融合后的轮廓生成位移图的 SVG 滤镜，由它显示整个融合形状下面的页面，玻璃自己的背景滤镜先关掉。快照引擎不用背板，因为 Safari 和 Chrome 都不能可靠地用 clip-path 裁背景滤镜：每块玻璃保留自己的圆角背景滤镜，压暗改由画布按融合后的形状只画一次，连接桥下面的页面从快照里取；磨砂到 2px 以上时，两层模糊叠在一起会露出下面那块的边缘，这时整个融合形状改由画布从快照画（已经模糊过，看不出分辨率低）。融合本身不截图，磨砂不大时玻璃后面仍是实时页面。高光和投影仍然每个像素只由一块玻璃负责：自己的内部归自己，重叠部分归画在最下面的那块，两块之间的连接桥归离得近的那块。在参数面板里新建几块面板，把它们拖到一起试试；不想融合的元素设 merge: false。

什么时候重拍快照

发生了什么SDK 怎么处理
拖动玻璃、滚动页面不重拍，只移动纹理上的采样位置
DOM 增删、属性或文字变化MutationObserver 发现后限频重拍
输入框打字监听 input 事件，限频重拍
页面尺寸变化、图片和字体加载完重拍
有限时长的 CSS 动画和过渡播放期间限频重拍
带 data-lg-live 的 canvas / video玻璃经过时每帧直接写进纹理
iframe、video、跨域图片、无限动画、data-lg-hole挖空，显示实时内容加玻璃高光

做了哪些优化

做法效果
内置截图：克隆 DOM，页面样式表原样交给浏览器画，不逐个读样式这张页面约 80–120 毫秒，modern-screenshot 要 1.3–1.6 秒（无 GPU 的测试机）
整页只拍一次，拖动和滚动只移动采样位置拖动不触发截图
只在内容变化时重拍；间隔 ≥ 250 毫秒且 ≥ 上次耗时的 4 倍，并放到浏览器空闲时执行截图最多占约 20% 主线程，不和拖动抢帧
纹理不生成 mipmap；亮度用 64 像素宽的小图算，不回读大图上传约 5 毫秒
中间平坦区域交给 CSS 模糊，WebGL 只算边缘一圈着色器的重活只在几个像素宽的环上
实时图层只在玻璃经过时上传自己那一小块不重拍整页
屏幕外的玻璃不绘制；所有玻璃共用一个 WebGL 上下文；大面板的投影范围有上限面板再多、再大，开销也基本只和屏幕上的玻璃有关
融合直接过滤实时页面，不截图；原生引擎的背板位移图只在玻璃相对位置变化时重建，按 1 个 CSS 像素一格生成，跳过离轮廓远的区域拖着融合中的玻璃时每帧约几毫秒，静止或整组移动时为零
每帧的测量和绘制排在页面自己的动画回调之后；拖动时指针柔光固定在手指下页面在动画循环里移动的玻璃当帧就画在新位置，不慢一帧；拖动中玻璃不用每帧重画

没有用 WebGPU：GPU 上的工作量本来就很小，瓶颈在截图，也就是 CPU 和 DOM。换成 WebGPU 不会更快，兼容性反而更差。

形状直接取元素自己的 border-radius。想要有颜色的玻璃，给元素写半透明的 CSS background 就行。

限制

  • 快照引擎的边缘不是严格实时的：静态内容看不出来，正在变化的区域会慢一两百毫秒。
  • 内置截图不会内嵌网络字体和 CSS 里 url() 引用的外部背景图，边缘里会用回退字体、缺背景图；需要时可以切到 modern-screenshot。
  • 页面上其他 position: fixed 的元素要加 data-lg-ignore，否则会出现在快照里的错误位置。
  • 需要滚动的面板，把 data-liquid-glass 放在外层，滚动放在内层。
  • 融合按两块玻璃在屏幕上的位置计算，没考虑它们各自的旋转和缩放。

页面上所有内容都是普通 DOM。玻璃元素自己不会进快照，所以不会折射自己。
